Status: ready-for-agent

## Problem Statement

Although Sparkkeep ships six Interface Locales (`en`, `ro`, `es`, `pt-BR`, `fr`, `de`), language selection is currently a purely browser-local UI chrome toggle that is disconnected from the rest of the application workflow:

1. **Disconnected Language Preferences:** Selecting a language in the Setup Wizard or Appearance preferences updates only browser local storage (`Interface Locale`), leaving the backend completely unaware of the workspace locale and leaving the AI `Output Language` set to English/source by default.
2. **Unlocalized Taxonomy & Raw Slugs:** The Configurable Taxonomy stores and renders raw English `Card Type` slugs (`article`, `video`, `book`, `guide`, `product`, `place`, `idea`, `quote`), while dropdown helpers translate only a partial legacy subset. Users in non-English locales see raw English taxonomy chips, and adding a Card Type by its localized name creates a disconnected custom string instead of resolving to the canonical built-in type.
3. **English-Only System Seeds:** Onboarding Demo Cards, immutable Built-in Playbooks, and Starter Profile Archetypes remain hardcoded in English even when a user selects Spanish, Romanian, Portuguese, French, or German during onboarding.
4. **Half-Localized AI Triage & Research Dossiers:** In the Triage pipeline, appending a general language instruction risks LLMs translating structural JSON schema enums (`horizon`, `worthiness.level`, `type`), causing validation fallbacks. In the Research pipeline, only the Verdict step and profile-enabled Custom steps receive the `Output Language` instruction—leaving Question Planning, Claim Verification, Competitive Landscape, and compiled Markdown report headings (`## Executive Verdict`, `## Claim Verification`, etc.) in English.
5. **No Way to Re-Synthesize Existing Cards:** While historical Cards and Research Dossiers properly remain immutable when switching languages, users lack a non-destructive action on an existing Card to regenerate its Triage Brief in their newly selected `Output Language`.
6. **English-Only Outbound Channels & Exports:** Outbound Telegram, Discord, Slack, and OpenClaw notifications, interactive triage buttons, scheduled digests, and Knowledge Sink Markdown section headings remain hardcoded in English regardless of the workspace language.

## Solution

Integrate multilanguage support end-to-end across the Sparkkeep workflow while preserving canonical routing and data integrity:

1. **Workspace Interface Locale Persistence & Smart Output Language Sync:** Persist the workspace `Interface Locale` in backend settings (keeping browser storage as an instant client cache). During Setup Wizard onboarding, picking an `Interface Locale` automatically aligns the AI `Output Language`. Post-onboarding switches automatically update `Output Language` if it was previously aligned with the `Interface Locale` (displaying a toast with a 1-click undo action to keep the previous AI language), while preserving custom `Output Language` overrides when decoupled.
2. **Canonical Card Types with Localized Display & Alias Resolution:** Keep all 15 known `Canonical Card Types` (`article`, `video`, `book`, `guide`, `product`, `place`, `idea`, `quote`, `tool`, `repo`, `paper`, `company`, `claim`, `tutorial`, `collection`, plus immutable `other`) stored and routed as canonical English slugs, while translating their display labels across every UI surface. When a user adds a Card Type in any supported locale, match localized names case- and accent-insensitively back to the canonical slug, and offer 1-click suggestion chips for inactive canonical types. Render user-defined `Custom Card Types` verbatim.
3. **Locale-Aware System Seeding & Playbook Cloning:** Dynamically localize the names, descriptions, and step titles of immutable `Built-in Playbooks` in the UI, and materialize those localized strings when a user clones a built-in playbook into a `Custom Playbook`. Localize Starter Profile Archetype prefills to the active locale, and seed the 6 Onboarding Demo Cards in the locale selected during the Setup Wizard.
4. **End-to-End Triage & Research Localization with Canonical Schema Enums:** Explicitly instruct Triage and Research LLM prompts to keep structural JSON schema enums (`type` for canonical types, `horizon`, `worthiness.level`, `signals`, `references.kind`, `status`, `recommendation`, `confidence`) in canonical English literals (backed by a normalizer reverse-lookup fallback for translated canonical card types), while generating all human-readable prose and `tags` in the target `Output Language`. Inject `Output Language` across every Research step (`plan`, `verify_claims`, `landscape`, `verdict`, and `custom` regardless of `UseProfile`), localize compiled Markdown report headings in both the report step and `Fallback Report Synthesizer`, and instruct Question Planning to write human-facing questions in the `Output Language` while optimizing web search queries for primary-source recall. Keep raw multimodal extraction (audio transcription and vision OCR) faithful to the source media's original language.
5. **Non-Destructive Triage Brief Regeneration:** Keep existing Cards and Research Dossiers immutable when the language changes, and add a **Regenerate Brief** action in the Card detail view that re-runs triage synthesis on the Card's stored capture in the current `Output Language` while preserving user-curated state (`Status`, `Horizon`, manual tags/actions, comments, and research history).
6. **Localized Outbound Channels & Knowledge Sink Headings:** Keep machine-readable metadata—YAML frontmatter keys and enum values in Obsidian/Joplin, Notion property keys, Outbox Feed JSON/Atom schema keys, and bot slash commands/callback IDs—strictly in canonical English for automation stability, while localizing human-readable Markdown body headings in Knowledge Sink exports and localizing outbound notifications, interactive button labels, and scheduled digests across Telegram, Discord, Slack, and OpenClaw using the persisted workspace `Interface Locale`.

## Implementation Decisions

1. **Workspace Interface Locale Persistence & API Contract:**
   - Persist `interface_locale` (one of `'en' | 'ro' | 'es' | 'pt-BR' | 'fr' | 'de'`, defaulting to `'en'`) in backend platform settings and expose it in the settings status and update payloads alongside `card_types`.
   - On the frontend, keep `localStorage` (`sparkkeep_locale`) as the synchronous initial cache, hydrate from the backend setting when workspace configuration loads, and persist updates to both `localStorage` and the backend settings API whenever the user changes locale in the Setup Wizard, Appearance tab, or language selector.
2. **Smart Coupling Between Interface Locale and Output Language:**
   - Maintain a helper mapping each `Interface Locale` code to its canonical `Output Language` name (`en` → `English`, `ro` → `Romanian`, `es` → `Spanish`, `pt-BR` → `Portuguese`, `fr` → `French`, `de` → `German`).
   - During the Setup Wizard, selecting an `Interface Locale` automatically sets the initial `UserProfile.Language` (`Output Language`) to the corresponding language.
   - Post-onboarding, when the user switches `Interface Locale` from `prevLocale` to `nextLocale`:
     - If `UserProfile.Language` was empty, default, or matched the language corresponding to `prevLocale` (indicating the user had not decoupled them), automatically update `UserProfile.Language` to match `nextLocale` and display a toast notification with a 1-click undo action to revert `UserProfile.Language` to its prior value.
     - If `UserProfile.Language` was explicitly customized to a different value (e.g., `"Same as source / English"` while in a non-English UI, or a third language like `"Japanese"`), preserve `UserProfile.Language` unchanged and surface a 1-click toast action allowing the user to align AI output with `nextLocale` if desired.
3. **Canonical Card Type Registry, Display Localization, and Alias Resolution:**
   - Define the complete set of 15 `Canonical Card Types` (`article`, `video`, `book`, `guide`, `product`, `place`, `idea`, `quote`, `tool`, `repo`, `paper`, `company`, `claim`, `tutorial`, `collection`, plus immutable fallback `other`) across backend and frontend catalog keys.
   - Every UI surface that renders a Card Type (Card badges, Card Modal type selector, Inbox/Board filters, Platform Preferences Taxonomy chips, and Playbook Studio routing pills) resolves the display label via the active locale catalog when the value is a `Canonical Card Type`, and renders the string verbatim when it is a `Custom Card Type`.
   - When adding or normalizing Card Types in Platform Preferences or the backend settings handler, normalize input (case-insensitive, trimmed, diacritic-insensitive) against both canonical English slugs and all registered locale display labels for the 15 `Canonical Card Types`. Matching inputs resolve to the canonical English slug (e.g., `"Herramienta"` or `"Instrument"` → `"tool"`).
   - In the Platform Preferences Card Taxonomy section, display inactive `Canonical Card Types` as 1-click quick-add chips alongside the free-text input for `Custom Card Types`.
4. **System-Seeded Content Localization (Demo Seed, Built-in Playbooks, Starter Archetypes):**
   - Extend `SeedDemoData` to accept or read the workspace `Interface Locale` and seed localized versions of the 6 showcase Cards and sample Research Dossier for all six supported locales (`en`, `ro`, `es`, `pt-BR`, `fr`, `de`).
   - For immutable `Built-in Playbooks` (`is_builtin: true`), resolve playbook names, descriptions, and built-in `Step Primitive` names dynamically from the active locale catalog in the UI. When a user clones/duplicates a `Built-in Playbook`, materialize the cloned `Custom Playbook` payload using the active locale's translated name, description, and step names so the editable copy starts in the user's language.
   - Localize the prefill values (`Goals`, `Skills`, `Stack`, `Interests`, `Constraints`) of the four Starter Profile Archetypes (`founder`, `finance`, `agriculture`, `systems`) in the locale catalogs so clicking an archetype populates the user's editable profile fields in the active `Interface Locale`.
5. **Triage & Research Prompt Discipline and Full Dossier Localization:**
   - Separate the `OUTPUT LANGUAGE INSTRUCTION` helper from profile personal-fit context so that an active `Output Language` is emitted even when personal profile fields are empty or when a custom research step has `UseProfile = false`.
   - Strengthen the `OUTPUT LANGUAGE INSTRUCTION` in Triage and Research prompts to explicitly mandate that all JSON keys and enumerated schema literals (`type` for canonical types, `horizon`, `worthiness.level`, `signals.extraction`, `signals.source_quality`, `references.kind`, `claims[].status`, `verdict.recommendation`, `verdict.confidence`, `verdict.suggested_horizon`) remain exact canonical English literals, while all prose fields (`title`, `tldr`, `why_care`, `claims`, `open_questions`, `worthiness.reason`, `discard_reason`, `rationale`, `one_liner`, `how_it_differs`, `for_whom`, `risks`, `next_actions`) and generated `tags` are written in the target `Output Language`.
   - Add a reverse-lookup fallback in Triage card normalization so that if an LLM returns a localized name of an active `Canonical Card Type`, it maps cleanly back to the canonical slug instead of falling back to `other`.
   - Inject the `Output Language` instruction into all LLM-driven Research steps: Question Planning (`plan`), Claim Verification (`verify_claims`), Competitive Landscape (`landscape`), Synthesis & Verdict (`verdict`), and Custom steps (`custom`).
   - In Question Planning (`plan`), instruct the model to write the human-facing `question` in the target `Output Language` while generating the web search `query` in the language best suited to retrieve authoritative primary sources for the subject.
   - Localize compiled Markdown headings and labels (`# Research:`, `## Executive Verdict`, `Recommendation`, `Confidence`, `For Whom`, `### Key Risks`, `### Recommended Next Actions`, `## Claim Verification`, `## Competitive Landscape & Alternatives`, `How it differs`, `## Questions & Findings`, `Search query`, `## Sources & Citations`) in both the `report` step and `Fallback Report Synthesizer` based on the active `Output Language` (falling back to the workspace `Interface Locale`, then English).
   - Keep raw multimodal extraction prompts (`Describe` for vision OCR and `Transcribe` for audio ASR) strictly source-faithful so transcripts and image digests preserve original-language text verbatim.
6. **Non-Destructive Triage Brief Regeneration:**
   - Add a `ReanalyzeCard` operation in the domain service and expose it via `POST /api/v1/cards/{id}/reanalyze`.
   - When invoked, fetch the Card's stored source capture (or reconstruct from the Card's `SourceURL` / `SourceNote` / `Title` for `Subject Cards`), run Triage synthesis using the current active taxonomy and `UserProfile` (including `Output Language`), and update the primary Card's AI-synthesized brief fields (`Title`, `Summary`, `ExecutiveSummary`, `ValueProposition`, `TLDR`, `WhyCare`, `Claims`, `OpenQuestions`, `Worthiness`, `Signals`, `References`, `SuggestedHorizon`, `SuggestedTags`, and `ProposedActions`) in place while preserving user-governed fields (`Status`, `Horizon`, user `Tags`, `CompletedActions`, `Comments`, and existing `Research` records).
   - Expose a **Regenerate Brief** button in the Card Modal header/actions with loading feedback and toast confirmation.
7. **Backend Localization Catalog for Knowledge Sinks, Channels, and Digests:**
   - Introduce a lightweight, zero-dependency Go localization catalog keyed by the six supported `Interface Locales` (`en`, `ro`, `es`, `pt-BR`, `fr`, `de`) for backend-rendered human headings and notification strings.
   - In Knowledge Sink Markdown formatters (Obsidian, Joplin, Notion body blocks, and Client Intent Markdown), keep all YAML frontmatter keys (`id`, `title`, `horizon`, `status`, `source_url`, `tags`, `created_at`, `updated_at`, `researched`), frontmatter enum values, Notion database property keys, and Outbox Feed schema fields in canonical English, while localizing the Markdown section headings (`## Executive Summary`, `## Summary`, `## Value Proposition`, `## Proposed Actions`, `## Source Notes`, `## References`, `## Research Dossier`, `**Playbook:**`, `**Completed:**`) using the workspace locale.
   - In Channel Adapters (Telegram, Discord, Slack, OpenClaw) and scheduled digest generators (`SendMorningDigest`, weekly digest), keep inbound bot slash commands (`/start`, `/help`, `/digest`, `/morning`, `/inbox`) and callback action prefixes (`do:`, `research:`, `keep:`, `shelve:`, `dismiss:`, `pb:`) canonical, while localizing outbound message copy, interactive button labels, and digest titles/headers using the workspace `Interface Locale`.

## Testing Decisions

1. **Good Tests Verify External Behavior at High-Level Seams:**
   - Tests must assert observable API responses, persisted domain state, generated prompt contracts, exported Markdown documents, outbound channel payloads, and rendered DOM text—never internal private helper state.
2. **Backend HTTP, Core Service, and Research Runner Seam:**
   - Following prior art in existing web, core, and research integration suites, test:
     - Workspace `interface_locale` persistence via settings endpoints, Setup Wizard alignment of `UserProfile.Language`, and localized `SeedDemoData` card creation across all 6 locales.
     - Canonical alias resolution when updating `card_types` (verifying localized inputs like `"Herramienta"` or `"Carte"` persist as `"tool"` / `"book"`, while custom strings persist verbatim) and normalizer fallback when an LLM returns a localized canonical type name.
     - Triage and Research prompt construction verifying canonical enum rules, decoupled `Output Language` injection across `plan`, `verify_claims`, `landscape`, `verdict`, and `custom` (with `UseProfile = false`), and localized Markdown report headings in `stepReport` and `FallbackReportSynthesizer`.
     - `POST /api/v1/cards/{id}/reanalyze` refreshing AI brief fields in the active `Output Language` while preserving `Status`, `Horizon`, `Comments`, `CompletedActions`, and `Research` runs.
     - Obsidian/Joplin/Notion Markdown generation preserving English YAML frontmatter keys/enums while localizing Markdown body headings, and Telegram/Discord/Slack/Digest outbound notifications rendering localized titles and interactive button labels.
3. **Frontend Component & Catalog Parity Seam:**
   - Following prior art in existing i18n parity suites and modal component tests, test:
     - Catalog key parity, placeholder parity, and coverage across all 6 locale catalogs for new taxonomy, archetype, built-in playbook, toast, and regenerate-brief keys.
     - Smart follow-unless-customized behavior when switching `Interface Locale`, including the 1-click undo/sync toast interaction.
     - Rendering localized labels for all 15 `Canonical Card Types`, 1-click inactive canonical type suggestion chips in Taxonomy settings, and verbatim `Custom Card Types`.
     - Rendering localized `Built-in Playbooks`, materializing localized strings when duplicating a built-in playbook, prefilling localized Starter Archetypes, and invoking **Regenerate Brief** in the Card Modal.

## Out of Scope

- Adding new UI locales beyond the six shipped languages (`en`, `ro`, `es`, `pt-BR`, `fr`, `de`).
- Automatic background bulk re-translation of existing Cards or Research Dossiers when switching languages.
- Translating raw audio transcripts (`ASR`) or raw vision OCR digests (`Describe`) prior to Triage synthesis.
- Translating YAML frontmatter keys, Notion database property names, Outbox Feed JSON/Atom field names, or bot slash command names (`/start`, `/digest`, `/morning`, `/inbox`).
- Right-to-left (RTL) layout mirroring.
